# Encountive Content Studio — Build Specification (Version 1\)

Working name — rename as you like. This document is a build brief for an AI coding agent (Claude Code). Build **version 1 only**. Sections marked **Future (v2)** are context for design decisions, not current scope. Reader note: the person directing this project is a novice developer building with AI assistance. Prefer clear, well-commented code and explain non-obvious choices.

---

## 1\. What we are building

A web application that generates marketing content for software products. Version 1 produces **social-media image carousels** and is for **internal use by Encountive** to market its own product portfolio. The same foundation will later add video and be offered to other companies as an Encountive product.

Build only the carousel version now, but keep the data model multi-tenant so the external product is a later addition rather than a rewrite.

Terminology: "Encountive" is the company/platform. This app is a new product within Encountive's portfolio.

---

## 2\. Technology stack

- **Database / storage / auth:** Supabase — Postgres, Storage buckets, Auth, and the `pgvector` extension for semantic search.  
- **Orchestration:** n8n — workflow automation that calls the AI and render APIs and handles the asynchronous submit-and-poll pattern.  
- **AI models (all Google; use the Gemini API to start, migrate to Vertex AI for the external product later):**  
  - Copywriting: Gemini text model.  
  - Image analysis / auto-titling: Gemini multimodal (vision) model.  
  - Image generation: Google's Gemini image model (the "Nano Banana" family). Note: Imagen 4 is cheaper but is scheduled for deprecation (around Aug 17, 2026), so prefer the Gemini image models for longevity. Verify the current model IDs in Google's documentation at build time — model names change frequently.  
  - Embeddings for semantic search: a Google text-embedding model. Set the database vector dimension to match whatever model you choose.  
  - Video — **Future (v2) only:** Veo 3.1. Do **not** target "Veo 3"; that specific model is deprecated/retired. Video is not part of v1.  
- **Render layer:** Creatomate — renders finished carousel images from templates, and also renders video later, so one vendor covers both formats. (Alternative: Contentdrips, carousel-specialized, also has an n8n integration.)  
- **Front end:** Recommended Next.js (React) with Tailwind CSS and the Supabase JavaScript client. Confirm with the project owner before committing if another stack is preferred.

---

## 3\. Critical constraints (do not violate)

1. **Multi-tenant from day one.** Every table carries an `org_id`. Enable Supabase row-level security so a user only sees rows belonging to their organization. Version 1 has exactly one organization (Encountive), seeded at setup.  
2. **No Midjourney in the automated pipeline.** Midjourney has no supported public API; automating it risks account bans. Use Google's image models for all generation. (Midjourney may still be used by hand, outside this app.)  
3. **Text is overlaid at the render layer, never generated into images.** AI-generated text inside images is unreliable and not editable. Generate clean background visuals; lay crisp, editable, on-brand text over them in Creatomate.  
4. **Asynchronous job pattern.** Render jobs (and future video jobs) are long-running. Every such step is: submit job → receive a job id → poll status until done (or receive a webhook) → fetch the file. Build one reusable polling sub-flow and reuse it.  
5. **Human approval before publishing (v1).** Nothing auto-publishes. A person reviews each carousel and approves or requests changes.

## 4\. Data model

Eight core tables plus a `profiles` table for authentication. All `id` columns are `uuid` primary keys; all tables have a `created_at timestamptz default now()`; all carry `org_id` (directly or via a parent) and are protected by row-level security.

**profiles** (links Supabase Auth users to an organization)

- `id` uuid PK, references `auth.users`  
- `org_id` uuid FK → organizations  
- `role` text (e.g. owner, editor)  
- `full_name` text

**organizations**

- `id` uuid PK  
- `name` text

**brand\_kits**

- `id` uuid PK  
- `org_id` uuid FK → organizations  
- `name` text  
- `colors` jsonb  
- `fonts` jsonb  
- `logo_url` text  
- `voice_guidelines` text

**assets** (the image library — uploaded and generated images live here together)

- `id` uuid PK  
- `org_id` uuid FK → organizations  
- `storage_path` text (path in the `assets` storage bucket)  
- `title` text (auto-generated by the vision model; editable)  
- `description` text (auto-generated; basis for the embedding)  
- `tags` text\[\]  
- `source` text — `uploaded` or `generated`  
- `status` text — lifecycle: `uploaded` → `analyzing` → `ready`  
- `mime_type` text, `width` int, `height` int  
- `embedding` vector(N) — N matches the chosen embedding model (commonly 768\)

**projects**

- `id` uuid PK  
- `org_id` uuid FK → organizations  
- `name` text  
- `status` text

**project\_assets** (join table — this IS the project board)

- `project_id` uuid FK → projects  
- `asset_id` uuid FK → assets  
- `position` int (display order on the board)  
- composite primary key (`project_id`, `asset_id`)

**content\_requests** (one carousel job)

- `id` uuid PK  
- `project_id` uuid FK → projects  
- `brand_kit_id` uuid FK → brand\_kits  
- `topic` text, `brief` text, `target_platform` text  
- `status` text — e.g. `queued` → `generating` → `in_review` → `approved`

**carousels**

- `id` uuid PK  
- `request_id` uuid FK → content\_requests  
- `status` text  
- `slide_count` int  
- `output_path` text (finished carousel in the `renders` bucket)

**slides**

- `id` uuid PK  
- `carousel_id` uuid FK → carousels  
- `position` int  
- `headline` text, `body_copy` text  
- `asset_id` uuid FK → assets (the image this slide uses — reused or newly generated)  
- `render_path` text (the finished slide image)

**Storage buckets:** `assets` (source/library images) and `renders` (finished carousels). Apply per-organization access policies.

**Semantic-search function:** create a Postgres function `match_assets(query_embedding, org_id, match_threshold, match_count)` that returns the asset rows for that organization whose embeddings are closest to `query_embedding` and above the threshold, ordered by similarity. Add a pgvector index on `assets.embedding`.

## 5\. Features (version 1 scope)

1. Brand kit — stored colors, fonts, logo, and voice guidelines applied automatically to every piece.  
2. Carousel generation from a brief — Gemini writes each slide's headline, body copy, and an image-need description.  
3. Render layer (Creatomate) — overlays editable, on-brand text onto chosen backgrounds; outputs finished slides.  
4. Bulk image upload — many images at once.  
5. Automatic vision analysis and titling — Gemini vision writes a title, description, and tags per image; user can edit.  
6. Asset library with semantic search — org-wide library searchable by keyword and by meaning (pgvector).  
7. Image reuse — search the library before generating; reuse close matches; save generated images back into the library for future reuse.  
8. Image-select page — gallery of `ready` images (thumbnails \+ auto-titles, keyword and semantic filtering) with multi-select.  
9. Projects and project boards — each project has a board (`project_assets`) holding selected images.  
10. Project-scoped reuse priority — generation searches the board first, then the wider library, then generates new.  
11. Human approval before publishing — review and approve/reject each carousel.  
12. Multi-tenant foundation — org-scoped tables with row-level security from day one.

## 6\. Workflows to implement (n8n)

**Workflow A — Bulk upload, analyze, title, embed**

1. Files uploaded in bulk to the `assets` bucket; one `assets` row created per file with `source = uploaded`, `status = uploaded`.  
2. For each new asset (process in parallel/batch): send the image to the Gemini vision model → receive title, description, tags → write them to the row.  
3. Generate an embedding from the description; save to `assets.embedding`; set `status = ready`.

**Workflow B — Image select to project board**

1. User opens the image-select page (shows only `ready` assets) and multi-selects.  
2. User attaches the selection to a project; write one `project_assets` row per selected image.

**Workflow C — Carousel generation (reuse-aware, project-scoped)**

1. Trigger: a `content_requests` row appears with `status = queued`.  
2. Load the brief and brand kit.  
3. Gemini text model writes the carousel — per slide: headline, body copy, and an image-need description.  
4. For each slide: embed the image-need description, then search in priority order — (a) the project's board, (b) the wider org library via `match_assets`, (c) if nothing clears the threshold, generate a new image with the Gemini image model, store it in the `assets` bucket \+ table (with description, tags, embedding, `source = generated`), and use it.  
5. Send slides (copy \+ chosen backgrounds \+ brand kit) to Creatomate; render finished slides (async: submit → poll → fetch).  
6. Save outputs to the `renders` bucket; update `carousels`/`slides`; set request `status = in_review`.  
7. On human approval, allow download/publish.

## 7\. Suggested build order

1. Scaffold the app; connect Supabase Auth; seed one organization (Encountive) and one user profile.  
2. Create the schema; enable `pgvector`; add row-level security policies; create `match_assets`.  
3. Bulk upload to the `assets` bucket with row creation.  
4. Workflow A — vision auto-titling \+ embeddings.  
5. Asset library UI with keyword \+ semantic search.  
6. Image-select page \+ projects \+ boards (Workflow B).  
7. Workflow C — carousel generation with reuse priority \+ Creatomate render.  
8. Review/approval screen (Feature 11).  
9. Polish \+ brand kit management UI.

Build and test one phase before moving to the next.

## 10\. Rough cost notes

- Copywriting: fractions of a cent per carousel.  
- Vision auto-titling: cents for dozens of images (batched).  
- Image generation: roughly $0.04–$0.13 per image when not reused; reuse drives this toward zero over time.  
- Render: Creatomate flat subscription, roughly $41–$50 per month.  
- A finished carousel: typically well under a dollar in variable cost.  
- Verify all model and service prices at build time — this category re-prices often.
